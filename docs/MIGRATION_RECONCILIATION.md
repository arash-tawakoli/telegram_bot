# Migration reconciliation

## Observed on 2026-09-05

Before this PR, GitHub contained 125 migration files and production recorded 139 migration entries. 62 repository version prefixes had no identical version in the production registry. Matching names suggest that some changes were deployed under different timestamps; this is not proof of 62 unapplied schema changes.

The previous assertion that every migration after the v2 baseline mirrored the exact production version is not supported by the current registry.

## Procedure followed

1. Compare both registries by version, name and actual SQL content.
2. Identify genuinely missing changes separately from timestamp differences.
3. Reconcile each entry with evidence. Do not blindly replay old bootstrap migrations or bulk-mark versions as applied.
4. Test the new lifecycle migration against an isolated Supabase environment with real PGMQ.
5. Apply the new additive migration before deploying the source worker that calls `finish_source_job_attempt`.
6. Drain old dispatcher invocations before enabling the dispatcher with delivery reservations.
7. Check advisors and operational queries after rollout. Keep source IDs and tier classifications stable.

The three new migrations were created with `supabase migration new` and applied before dependent functions. The exported directory now contains all 142 actual production versions. `migration-registry.json` records names, original SQL hashes, export hashes and retired repository paths. The 62 mismatched historical filenames were replaced by actual registry versions; no historical migration was blindly replayed or marked applied.

Two historical SQL bodies embedded credentials. Their exports resolve nine distinct values from Vault through `get_bot_secret('migration_credential_<digest>')`. The original registry hashes remain recorded. These exports require separately provisioned Vault values when reconstructing another environment; they are not credential-free one-command bootstrap scripts. No production registry statements were rewritten.

Validation includes PGlite fixtures and a real PostgreSQL/PGMQ integration transaction: a synthetic queued message, attempt-fenced acknowledgement/archive, Telegram inbox retry, and referral ACL checks. The transaction was rolled back. No real Telegram message was generated by that integration test.

Dispatcher cron was drained during cutover, then re-enabled. Its HTTP timeout is 145000 ms; its schedule remains every minute. The subsequent v30 dispatcher hotfix and real-delivery checks are documented in [rollout](ROLLOUT_2026-09-05.md).

See [the review](ARCHITECTURE_REVIEW_2026-09-05.md) for findings, current limits and rollback notes.
